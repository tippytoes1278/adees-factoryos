# Investigation Findings — 23 Jul 2026

Read-only investigation of the three LIVE incidents from the 22 Jul session.
Evidence: code audit of HEAD + LIVE sheet (1FLPeuQF…) + REQUESTS data. Execution-log
timestamp check was cut short (Chrome drop), but REQUESTS approval timestamps cover it.

## Issue 1 — Master Activities submissions vanish

**Root cause (confirmed):** Master Activities submit (`js_arvind.html` ~1292) sends
`{dept, activityName, rate, comm}` — no `sheet` — into `requestActivitySetup()`
(`activities.js` ~717), the per-order handler. Its "already approved" guard matches on
`safeStr(pl.sheet) === safeStr(item.sheet)`; for master-style payloads both sides are `''`,
so **one APPROVED master activity in a dept blocks every future master submission for that
dept, permanently**, with the order-setup error text.

**Evidence:** LIVE REQUESTS has approved master-style ACTIVITY_SETUP rows (REQ-063 Texon
Cutting / cutting, REQ-052..055 lasting/finish/dispatch, etc.). MASTER_ACTIVITIES has
approved entries in **all six departments → every dept locked**. Punch + Hand Lasting are
absent from MASTER_ACTIVITIES — batch is rejected on first blocked item BEFORE any write
(hence "no row reached REQUESTS"). Error surfaced only as a transient toast — not silent
server-side.

**Fix direction:** dedicated MASTER_ACTIVITY request type end-to-end; harden the
requestActivitySetup guard to never match on empty sheet.

## Issue 2 — ART-024 collision on WO-2026-047

**Root cause:** NOT the Speed-3 cache — `createOrder()` numbers ARTs from live
`ss.getSheets()`. But `processRequest` → `createOrder` takes **no LockService lock** (only
`submitRequest` locks). REQUESTS rows 131/132/133 (incl. WO-2026-046/047) were all approved
at **22-Jul-2026 12:26 — the same minute**: overlapping executions both read max=ART-023.
`template.copyTo()` → `setName('ART-024')` threw on the duplicate, stranding
"Copy of ART-TEMPLATE" (no cleanup in the failure path). Retry saw ART-024 and produced
ART-025. 1.13 failure handling (row reset to PENDING) worked as designed.

**Evidence:** sheet inventory shows ART-001…ART-025 with "Copy of ART-TEMPLATE" sitting
between 024 and 025; gaps at ART-004/005/008/011 (old deletes). The copy is template-only
(blank article/customer/qty) — safe to delete.

**Fix direction:** script lock around order/sheet creation; retry on setName collision;
delete the stranded copy when rename fails; `auditArtSheets()` for the orphan question.

## Issue 3 — Home "1 pending" vs Requests tab 0

**Root cause:** stale cache, not a type filter. Home tile reads `pendingCount` from
`getDashboardData`'s `dashboardData_<ENV>` ScriptCache entry (300 s TTL,
`payments.js` ~60/299); the Requests tab reads live via `getPendingRequests`.
`submitRequest` / `processRequest` / `rejectRequest` (and the other REQUESTS writers in
activities.js) **never invalidate that cache** — payments/jobcards/orders/contractors
flows all do. Approving the last pending request leaves Home at 1 for up to 5 min.

**Evidence:** LIVE REQUESTS currently has ZERO PENDING/REVISION rows; only 3 REJECTED
(REQ-024 PAYMENT_SUBMISSION, #25 EDIT_REQUEST, #62 NEW_ORDER 15-Jun).

**Fix direction:** invalidate `dashboardData_<ENV>` in every function that writes or
updates REQUESTS rows.

## Cross-cutting theory verdict

Stale CacheService reads explain **Issue 3 only**. Issue 1 = routing/guard flaw,
Issue 2 = missing lock. Three independent fixes.
